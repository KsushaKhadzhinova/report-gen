# Диаграмма вариантов использования

Сначала прочитай `diagram-common`. Образец: `../assets/diagram-tools/examples/usecase.puml`.

## Что нужно на входе

- Из карты проекта (`project-map.md`): роли и то, что каждая может делать; внешние системы. Нет: сначала `analyze-project-code`.
- Из брифа: нужны ли таблицы описания вариантов использования. Пусто: спроси «Нужны ли в записке таблицы с пошаговым описанием вариантов использования, или достаточно диаграммы с перечнем действующих лиц?» По умолчанию достаточно диаграммы.

## Правила

**Варианты использования**
1. **Название начинается с глагола:** «Добавить товар», «Просмотреть список товаров», «Сформировать отчёт». Существительные («Управление товарами», «Статистика») не допускаются.
2. **Один вариант описывает одну задачу.** «Добавить и изменить товар» разбивается на два. «Включить и отключить уведомления» на два.
3. **CRUDL по главному объекту системы.** Для объекта, которым пользователь управляет, показаны все пять операций отдельными вариантами: создать, просмотреть список, просмотреть одну запись, изменить, удалить. Если какой-то операции в проекте нет, её нет и на диаграмме, а в тексте это оговорено.
4. Только реально существующие функции (по карте проекта).
5. Фоновые процессы системы (опрос внешнего источника, обновление справочника) показываются как варианты, связанные с внешней системой.

**Актёры**
6. Роли пользователей слева, внешние системы справа или снизу со стереотипом «внешняя система».
7. Если одна роль включает возможности другой, показывается обобщение (администратор наследует пользователя), а общие варианты не дублируются.

**Связи**
8. `include`: обязательная часть сценария (добавление товара включает проверку лимита). `extend`: необязательное дополнение.
9. Связей столько, сколько нужно для понимания; сеть пересекающихся пунктиров упрощается.

**Вид**
10. **Без рамки системы:** актёры и варианты стоят без общего прямоугольника.
11. Шрифт Arial, без курсива (в образце курсив стереотипов отключён), без теней.
12. Компоновка: актёр слева, варианты столбцом (`left to right direction`). Диаграмма получается высокой и хорошо вставляется в страницу.
13. До 20–22 вариантов; длинные названия переносятся на две строки (`\n`).

## Как строить

```bash
cd <папка исходников диаграмм>
cp examples/usecase.puml usecase.puml     # замени актёров, варианты, связи
./render.sh usecase.puml 0.95 14
pdftoppm -r 70 -png usecase.pdf просмотр
```

Настройки вида в начале образца (`skinparam`, направление) оставь без изменений.

## Текст раздела

После диаграммы:
- перечень действующих лиц с одной фразой о каждом;
- группы вариантов по смыслу (управление объектом, уведомления, отчёты, настройки, администрирование);
- вывод о разграничении функций между ролями.

Названия вариантов в тексте совпадают с диаграммой дословно.

## Таблицы описания вариантов (только если в брифе «да»)

Формат строк в `../assets/formats.md`: идентификатор и название, основное действующее лицо, предварительные условия, основной поток, расширения, выходные условия. Вёрстка через `longtable` (скил `latex-formats`), внутри таблиц ничего не выделяется жирным. Таблиц столько, сколько ключевых сценариев, обычно пять-семь.

Если пользователь просит убрать описания вариантов использования:
- удали таблицы вместе с метками и строками «Продолжение таблицы»;
- удали фразы, которые на них ссылаются («сценарии приведены в таблицах 2.1–2.7»);
- поправь слова, отсылавшие к таблицам («большая часть сценариев» на «большинство вариантов использования»);
- убери ручные разрывы страниц, поставленные ради этих таблиц;
- проверь, что нумерация остальных таблиц пересчиталась и ссылки разрешились.

## Проверка

- [ ] каждое название начинается с глагола;
- [ ] нет вариантов с союзом «и», объединяющих две задачи;
- [ ] по главному объекту есть создание, список, просмотр, изменение, удаление;
- [ ] нет рамки системы;
- [ ] только Arial, кегль на странице не ниже 9 пт;
- [ ] названия в тексте совпадают с диаграммой.
