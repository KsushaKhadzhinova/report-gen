# Анализ кода проекта

Результат: файл `project-map.md` рядом с брифом. На него опираются все разделы записки. Проект анализируется один раз: код считается завершённым и не меняется.

## Что нужно на входе

Из `coursework-brief.md`: локальная папка проекта. Пусто: спроси «Где лежит готовый проект: ссылка на GitHub или путь к папке?» (клонирование описано в `coursework-start`). Запиши путь к карте в бриф.

## Запрет

Проект открыт только на чтение. Не правь код, не запускай миграции на рабочей базе, не меняй конфигурацию, не коммить в репозиторий проекта. Запускать можно только то, что ничего не меняет: чтение метаданных схемы на базе в памяти, тесты, если они не трогают внешние сервисы.

## Что прочитать

1. Структура папок и точки входа, README, файлы зависимостей, конфигурация, файлы развёртывания (Docker, compose).
2. Работа с базой данных: модели или DDL, миграции, запросы, индексы, ограничения, внешние ключи с правилами удаления.
3. Получение внешних данных: клиенты API, парсеры, ограничения частоты запросов.
4. Обработка: фоновые задачи, планировщик, бизнес-правила, очереди.
5. Доставка результата пользователю: уведомления, отчёты, экспорт и импорт.
6. Интерфейс: обработчики команд, экраны, роли и права.
7. Тесты: что ими покрыто.

Для первого знакомства со стеком подходит готовый промт `../assets/prompts/z1_stack.md`.

## Что записать в `project-map.md`

1. **Назначение системы** одним абзацем.
2. **Стек:** язык, СУБД, библиотеки, способ развёртывания; для каждой технологии зачем она в проекте.
3. **Модули:** из каких частей состоит проект, что делает каждая, как они взаимодействуют. Словами, по поведению и назначению.
4. **Данные:** сущности предметной области, таблицы и столбцы с типами, ключи, связи и их мощность, индексы (и под какие запросы), ограничения целостности, резервное копирование.
5. **Ключевые процессы** по шагам: два-три главных (например, цикл опроса, обработка записи, доставка уведомления), с условиями ветвления. Это основа схем алгоритмов и диаграмм последовательности.
6. **Роли и сценарии:** что может каждая роль, какие команды и экраны есть.
7. **Реализовано** из перечня возможностей в задании: таблица «возможность, статус, где в проекте».
8. **Не реализовано:** чего нет. Это материал для направлений развития в заключении.
9. **Числа и факты**, пригодные для текста: интервалы, лимиты, объёмы. Только те, что видны в коде или конфигурации.
10. **Расхождения и дефекты:** места, где поведение отличается от ожидаемого, отсутствующие правила удаления, лишние индексы. Отдельным списком, без правки кода.
11. **Реальные имена для диаграмм:** таблицы, столбцы, классы, функции. Этот раздел единственный, где приводятся имена из кода.

## Правила изложения

- В разделах 1–9 карты и затем в тексте записки не цитируй код и не называй переменные, функции и классы по именам. Описывай поведение и назначение.
- Имена из кода используются только на диаграммах, где это требуется (логическая и физическая схемы, диаграмма классов), и в тексте, который эти диаграммы описывает. Для этого служит раздел 11 карты.
- Каждое утверждение карты должно подтверждаться кодом. Не уверен: пометь «не проверено» и не используй в тексте как факт.
- Не оценивай качество кода, если пользователь не просил.

## Если в проекте используется ORM

Проверь в брифе поле «Упоминание ORM». Если записано «не упоминать»: в карте опиши работу с базой в терминах SQL (какие запросы выполняются, какие транзакции), а схему бери из фактических таблиц. В раздел расхождений добавь строку: «в коде используется ORM, в записке работа с базой описана через SQL по решению пользователя».

## Сверка текста с кодом

Когда раздел записки написан, сверь его с картой: число сущностей, названия ролей, интервалы и лимиты, перечень возможностей. Нашёл расхождение текста с кодом: исправь текст. Нашёл дефект в коде: запиши в раздел 10 и сообщи пользователю, код не правь.

После завершения покажи пользователю краткую карту (разделы 1–3 и 7–8) и спроси, всё ли верно, прежде чем писать текст.

Источник: K1 (карта без цитат кода и имён), Z1 (стек), K3–K6 («что реально реализовано», «чего пока нет»), K4 (ORM), замечание о найденных дефектах из переписки по записке.
